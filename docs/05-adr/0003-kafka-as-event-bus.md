# ADR-0003. Apache Kafka как брокер событий и команд

- **Статус:** принято
- **Дата:** 2026-11-05

## Контекст

Через брокер проходят три типа трафика с разными свойствами:

| Поток | Объём (оценка на 3000 машин) | Требования |
|---|---|---|
| События аренды и платежей | ~10-50 в секунду в пике | Не терять; порядок в пределах аренды; несколько независимых подписчиков; возможность перечитать |
| Команды машинам | ~5-20 в секунду | Порядок в пределах машины (Unlock не должен обогнать Lock) |
| Телеметрия | 3000 машин × 1 точка за 5-10 с = **300-600 в секунду** | Высокая пропускная способность, допустимы дубликаты |

Ещё одно требование: на защите и при отладке нужно уметь проигрывать события заново, то есть перечитать топик новым консьюмером или после исправления бага.

## Варианты

| | **A. Apache Kafka** | **B. RabbitMQ** | **C. NATS JetStream** | **D. Без брокера (только REST + вебхуки)** |
|---|---|---|---|---|
| Модель | Лог с партициями, консьюмер сам хранит offset | Очереди, сообщение удаляется после ack | Поток с consumer-группами | Прямые вызовы |
| Порядок по ключу | Да, в пределах партиции | Только в одной очереди с одним консьюмером | Да, по subject | Нет |
| Несколько подписчиков | Consumer groups, бесплатно | Fanout exchange + очередь на подписчика | Да | Каждый вызов вручную |
| Перечитывание (replay) | Да, по offset или времени | Нет (кроме stream-очередей в 3.9+) | Да | Нет |
| Пропускная способность для телеметрии | Отлично | Хорошо | Отлично | Плохо |
| Задержки, ретраи, DLQ «из коробки» | DLQ вручную (`*.DLT`) | Да (DLX, TTL) | Частично | Нет |
| Порог входа и опыт команды | Средний; много материалов, Spring Kafka, sarama/franz-go | Низкий | Низкий, но мало материалов | Низкий |
| Ресурсы в docker-compose | KRaft-режим, 1 контейнер в dev | 1 контейнер | 1 контейнер | Не нужны |

## Решение

Выбираем **A: Apache Kafka** (режим KRaft, без ZooKeeper).

- Топики и ключи описаны в таблице в [02-c4-container.md](../02-c4-container.md#топики-kafka). Ключом партиции служит идентификатор агрегата, чьи инварианты мы защищаем (`rentalId` или `carId`).
- Продюсеры: `acks=all`, `enable.idempotence=true`. В prod `replication.factor=3`, `min.insync.replicas=2`; в dev один брокер, RF=1.
- Консьюмеры: ручной commit offset после commit транзакции в БД (вместе с inbox из ADR-0002).
- Ретраи на стороне консьюмера: 5 попыток с бэкоффом в памяти, затем запись в `<topic>.DLT` и алерт.
- Отложенные действия (таймер брони, повтор списания долга) делаются не через брокер, а через таблицу `scheduled_jobs` в сервисе-владельце. В Kafka нет отложенной доставки, а эмулировать её топиками-задержками сложнее, чем поллить таблицу.

## Последствия

**Плюсы**
- Один брокер покрывает все три потока, включая телеметрию.
- Replay помогает в отладке, при добавлении нового консьюмера (например, аналитики) и при восстановлении проекций (Fleet может перестроить положение машин).
- Порядок по ключу исключает гонки внутри одной сущности: команды одной машине и события одной аренды обрабатываются строго последовательно.

**Минусы**
- Нет встроенных DLQ и отложенных сообщений. Делаем свой `.DLT` и `scheduled_jobs`.
- Kafka сложнее в эксплуатации, чем RabbitMQ. Для учебного стенда хватает одного контейнера в KRaft-режиме и UI (Kafka UI или Redpanda Console).
- Число партиций ограничивает параллелизм консьюмеров. 12-48 партиций хватает с запасом. Увеличить их число можно и позже, но тогда изменится распределение ключей по партициям, поэтому делать это стоит только при нулевом consumer lag.
- Если во второй части Kafka окажется слишком тяжёлой, её можно заменить на Redpanda. Она совместима по протоколу, контракты и код менять не придётся.
