# ADR-0004. Эксклюзивность машины: условное обновление в Fleet и страховочный lease

- **Статус:** принято
- **Дата:** 2026-11-05

## Контекст

Главный инвариант системы: в каждый момент машина принадлежит не более чем одной аренде. Типичная гонка: два пользователя видят одну свободную машину у станции метро и нажимают «Забронировать» в одну и ту же секунду. Вторая проблема: машина зарезервирована, а аренда потерялась (Rental упал, таймер не сработал). Тогда машина навсегда пропадает с карты.

## Варианты

| | **A. Распределённая блокировка (Redis / Redlock)** | **B. Rental проверяет статус, потом Fleet меняет** | **C. Условное атомарное обновление во Fleet** | **D. Резерв через очередь (одна партиция на машину)** |
|---|---|---|---|---|
| Суть | `SET car:{id} NX PX` перед резервом | `GET /cars/{id}`, и если AVAILABLE, то `PUT status` | `UPDATE … WHERE status='AVAILABLE'` в БД владельца | Запросы на резерв в топик с ключом `carId`, Fleet обрабатывает последовательно |
| Корректность | Есть пограничные случаи (паузы GC, истечение TTL, failover Redis) | Некорректно: check-then-act даёт гонку | Корректно: атомарность даёт сама БД | Корректно |
| Новая инфраструктура | Redis | Нет | Нет | Нет |
| Задержка ответа пользователю | +1 запрос | +1 запрос | минимальная | асинхронно: пользователь ждёт события |
| Что, если аренда потерялась | Ключ истечёт по TTL, но статус в БД останется | Машина зависнет | Нужен отдельный механизм | Нужен отдельный механизм |

## Решение

Выбираем **C: условное атомарное обновление в БД Fleet** и дополнительно страховочный lease.

1. Статусом машины владеет только Fleet. Другие сервисы не меняют его и не читают из БД Fleet.
2. Резерв выполняется одним запросом:
   ```sql
   UPDATE cars
      SET status = 'RESERVED', current_rental_id = :rentalId,
          lease_until = :leaseUntil, version = version + 1
    WHERE id = :carId
      AND (status = 'AVAILABLE' OR current_rental_id = :rentalId)  -- второе условие = идемпотентный повтор
   RETURNING *;
   ```
   Если запрос вернул 0 строк, ответ `409 CAR_NOT_AVAILABLE`. Достаточно стандартного уровня изоляции `READ COMMITTED`: PostgreSQL блокирует строку на время `UPDATE`, и второй запрос увидит уже обновлённый статус.
3. Дополнительная защита на уровне схемы: `CREATE UNIQUE INDEX ON car_reservations(car_id) WHERE released_at IS NULL`.
4. **Lease.** Резерв создаётся с `leaseUntil`, равным концу бесплатной брони плюс 5 минут. Job во Fleet раз в минуту освобождает машины в статусе `RESERVED` с `lease_until < now()` и публикует `CarReservationLapsed`. Rental, получив событие, переводит аренду из `RESERVED` в `EXPIRED` и снимает hold. Для аренды в любом другом статусе событие игнорируется. После `RentalStarted` lease не действует: статус `IN_TRIP` job не трогает.
5. Основной таймер истечения брони остаётся в Rental. Lease нужен только как страховка на случай, если основной механизм не сработал.

## Последствия

**Плюсы**
- Корректность обеспечивает PostgreSQL, без Redis и распределённых блокировок.
- Повтор запроса с тем же `rentalId` безопасен: сетевые ретраи от Rental к Fleet не создают проблем.
- Машина не может застрять в резерве дольше `leaseUntil`, даже если Rental полностью потерял состояние.

**Минусы**
- Два таймера (в Rental и lease во Fleet) могут сработать почти одновременно. Это безопасно: оба ведут к одному исходу, а переходы в Rental защищены условием на текущий статус.
- Есть окно, когда Fleet уже освободил машину по lease, а пользователь в эту секунду нажал «Начать». Rental получит `CarReservationLapsed` и откажет в старте (`409`). Lease на 5 минут длиннее брони, поэтому на практике это возможно только при сбое Rental.
- Пропускная способность резервов ограничена одной строкой на машину. Для каршеринга это не проблема: за одну машину одновременно борются единицы запросов.
