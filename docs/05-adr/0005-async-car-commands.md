# ADR-0005. Асинхронные команды машине через Telematics Gateway с дедлайном

- **Статус:** принято
- **Дата:** 2026-11-05

## Контекст

Чтобы открыть или закрыть машину, нужно отправить команду в IoT-платформу провайдера. Та передаёт её телематическому блоку по сотовой связи. Свойства этого канала:

- выполнение занимает от 1-3 секунд до бесконечности (машина в подземном паркинге, нет сети, сел АКБ);
- подтверждение приходит асинхронно колбэком, иногда дважды, иногда уже после того, как мы перестали ждать;
- машина может отклонить команду (`LOCK` при открытой двери);
- API и модель данных провайдера чужие, провайдера могут сменить.

Если Rental вызывает провайдера синхронно и держит HTTP-соединение до подтверждения, то при недоступности машины поток висит, а пользователь видит бесконечный спиннер. После таймаута непонятно, открылась ли машина.

## Варианты

| | **A. Синхронный вызов провайдера из Rental** | **B. Синхронный вызов Telematics, который ждёт колбэк** | **C. Команда через Kafka в Telematics, результат событием** |
|---|---|---|---|
| Где живёт логика ретраев | В Rental | В Telematics | В Telematics |
| Команда переживёт рестарт сервиса | Нет | Нет | Да, она лежит в топике и в журнале `car_commands` |
| Поздний ответ машины | Теряется | Теряется | Публикуется с флагом `lateAfterTimeout` |
| Порядок команд одной машине | Не гарантирован | Не гарантирован | Гарантирован ключом партиции `carId` |
| Изоляция от провайдера | Нет: модель провайдера протекает в домен | Да | Да |
| UX | Спиннер до таймаута HTTP | Так же | `202 Accepted`, затем push или опрос статуса |

## Решение

Выбираем **C: асинхронные команды через Kafka** в отдельный сервис-адаптер Telematics Gateway (anti-corruption layer).

- Rental кладёт `UnlockCar` или `LockCar` в outbox. У команды есть `commandId` и `deadline`: 60 секунд на открытие, 120 на закрытие.
- Telematics пишет команду в `car_commands` (`UNIQUE(command_id)`, повтор не исполняется) и отправляет провайдеру. Пока нет подтверждения, повторяет с экспоненциальным бэкоффом (1, 2, 4, 8, 16 с) до `deadline`.
- Результат публикуется в `telematics.events`: `CarUnlocked`, `CarLocked` или `CarCommandFailed{TIMEOUT | REJECTED | DEVICE_ERROR}`.
- Подтверждение, пришедшее после `deadline`, не выбрасывается, а публикуется с `lateAfterTimeout=true`. Решение о компенсации (`LockCar(COMPENSATION)`) принимает Rental, потому что только он знает состояние аренды ([сценарий сбоя 1](../04-main-process.md#сценарий-сбоя-1-машина-не-открылась)).
- Telematics нормализует модель провайдера: переводит `deviceId` в `carId`, а коды ошибок в наш enum. Остальная система с моделью провайдера не работает.
- Для второй части пишем симулятор провайдера. Его поведение задаётся конфигом (задержка, доля потерянных ответов, офлайн-машины), поэтому все три сценария сбоя можно показать вживую.

## Последствия

**Плюсы**
- Пользователь получает понятный ответ не позже чем через 60 секунд, и при этом никакой поток не висит.
- Команда не теряется при рестарте Rental или Telematics.
- Unlock и Lock одной машины не переупорядочиваются.
- Провайдера можно сменить, переписав только Telematics Gateway.

**Минусы**
- Клиенту нужен асинхронный UX: состояние `STARTING` / `FINISHING`, push или опрос `GET /rentals/{id}` раз в секунду.
- Появляется ещё один сервис и ещё одна точка отказа. Если Telematics недоступен, команды ждут в топике, пользователь получит таймаут саги и компенсации (Rental тоже отслеживает дедлайн команды по `scheduled_jobs`, на случай, если Telematics вообще не ответил).
- Нужно отдельно обработать случай, когда машина открылась после отмены, иначе она останется открытой. Для этого есть компенсирующая команда и алерт оператору.
