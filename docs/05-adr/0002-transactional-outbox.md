# ADR-0002. Transactional outbox + inbox: at-least-once с идемпотентными консьюмерами

- **Статус:** принято
- **Дата:** 2026-11-05

## Контекст

Каждый шаг саги состоит из двух действий: изменить своё состояние в БД и сообщить об этом другим через Kafka. Если выполнять их двумя независимыми операциями (dual write), возможны две аварии:

1. Статус в БД сменился на `ACTIVE`, а сервис упал до публикации `RentalStarted`. Fleet не узнает, что машина в поездке.
2. Событие ушло в Kafka, а транзакция БД откатилась. Billing спишет деньги за поездку, которой в базе Rental нет.

Кроме того, брокер доставляет сообщения по схеме at-least-once: после ребалансировки консьюмеров или рестарта одно и то же событие может прийти повторно. Без защиты это приведёт к двойному списанию.

## Варианты

| | **A. Dual write** | **B. 2PC / XA между БД и брокером** | **C. Transactional outbox + inbox** | **D. CDC (Debezium) из outbox** |
|---|---|---|---|---|
| Атомарность «состояние + событие» | Нет | Да | Да | Да |
| Поддержка Kafka | Да | Нет (Kafka не участвует в XA) | Да | Да |
| Инфраструктура | Ничего дополнительного | Координатор транзакций | Только таблица и relay-поток в сервисе | Kafka Connect + Debezium |
| Задержка публикации | минимальная | высокая | 100-500 мс (поллинг) | ~100 мс |
| Сложность для учебного проекта | низкая, но решение некорректное | неприменимо | средняя | высокая |

## Решение

Выбираем **C: transactional outbox для публикации и inbox для приёма**. Переход на D возможен без изменения контрактов.

**Outbox (продюсер):**
```sql
CREATE TABLE outbox (
  id            uuid PRIMARY KEY,          -- = eventId в заголовке
  aggregate_id  uuid NOT NULL,             -- ключ партиции (rentalId / carId)
  topic         text NOT NULL,
  event_type    text NOT NULL,
  payload       jsonb NOT NULL,
  headers       jsonb NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  published_at  timestamptz
);
```
Бизнес-изменение и `INSERT INTO outbox` выполняются в одной транзакции. Relay-поток раз в 200 мс читает `WHERE published_at IS NULL ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED`, публикует с `acks=all` и проставляет `published_at`. Если relay упал после публикации, но до обновления `published_at`, событие уйдёт повторно. Это допустимо, дубликаты отсекает inbox.

**Inbox (консьюмер):**
```sql
CREATE TABLE inbox (
  event_id     uuid PRIMARY KEY,
  event_type   text NOT NULL,
  processed_at timestamptz NOT NULL DEFAULT now()
);
```
Событие обрабатывается в одной транзакции. Сначала `INSERT INTO inbox … ON CONFLICT DO NOTHING`. Если вставлено 0 строк, это дубликат, и событие пропускается. Иначе выполняется бизнес-логика, затем commit, затем commit offset в Kafka.

**Естественные ключи идемпотентности.** Дополнительно используются `UNIQUE(rental_id)` на счёте, `UNIQUE(command_id)` в журнале команд и ключи PSP `{rentalId}:{operation}`. Они защищают и тогда, когда одно и то же действие пришло разными путями, например через вебхук и через опрос.

## Последствия

**Плюсы**
- Ни одно событие не теряется: если транзакция закоммичена, событие будет опубликовано.
- Дубликаты безвредны, поэтому поверх доставки at-least-once получается эффект exactly-once.
- Kafka может быть недоступна несколько минут, сервисы продолжают работать, события копятся в outbox.

**Минусы**
- Публикация задерживается до 0,5 с. Для нашего процесса это незаметно, машина всё равно отвечает за секунды.
- Таблицы растут. Опубликованные записи outbox старше 3 суток удаляет job, inbox чистится старше 30 суток (это больше retention самого длинного топика).
- Порядок публикации гарантирован только в пределах одного `aggregate_id`. Этого достаточно, потому что все наши инварианты привязаны к одной аренде или одной машине.
- Каждый сервис реализует один и тот же шаблон, поэтому для каждого языка делаем небольшую общую библиотеку (outbox relay и inbox-декоратор обработчика).
